# Teach for understanding

Choose a concrete learning target: trace an input through one component, explain
why an operation is needed, or assess what an experiment supports. A long summary
or repeated definitions do not demonstrate this understanding.

Start from a specific example. Explain one operation before naming it. For a
formula, identify each symbol, shape when known, operation and one limit case.
For a table, identify dataset, split, metric, direction and unit before comparing
rows. Inspect the original page for equations or figure labels. An analogy is
an intuition, not a substitute for the paper's assumptions.

Ask one short transfer question instead of requesting a repetition:

- What would change if this component were removed?
- Which quantity is being predicted, and which is supplied as input?
- Does this table establish cross-dataset generalization? Why?
- If we change only the data split, can these results still be compared?

Stop for the actual response. Separate the correct portion, the precise
misunderstanding and the source-supported correction. Do not call an incorrect
answer correct to be encouraging. If your question is ambiguous, acknowledge it
and mark the judgment uncertain rather than blaming the learner.

`understood` applies to this target, not the entire paper. `needs_review` should
preserve a concrete misconception; return to it with a different example or
smaller question. `uncertain` means evidence or the answer does not justify a
confident judgment. Check the review queue before introducing advanced concepts.
Do not count a restatement of your own explanation as independent evaluation or
claim learning gains without actual users.
